# A氏への移転設計 — 「向け直し」で渡る部分と、新規獲得が要る部分

> 前提: A氏は人に対する委任・伝達の経験（部下やチームメンバーへの任せ方）を既に持っているものとする。
> 設計方針: 02の検証結果に基づき、「人に対する既存の力をAIに向け直す」経路を主線に、AI固有スキルだけを新規学習として切り出す。

## レイヤー0: 最初に渡すべき一文

**「部下がAIエージェントに変わっただけ」**（本人の言葉、00[14]）。

注: この一文は仮説の証拠としては使えない（本人のセルフイメージの表明。02参照）が、**教材の導入としては最も効く**。A氏への移転はこの一文から始めるのが最も安い。「AI活用スキルを学ぶ」というフレーミングを捨てさせ、「あなたが既にやっている部下への任せ方を、新しい部下に適用する」と再定義する。ただしこの一文には後述の重大な但し書き（レイヤー2）が3つ付く。

## レイヤー1: 向け直しで渡るもの（既存スキルの適用先変更）

A氏が人に対して既に持っているはずの判断を、そのままAIに向ける。教材は 03-decision-patterns.md の対応パターン。

| A氏が既に持っている力 | AIへの向け直し | 対応パターン |
|---|---|---|
| 部下の力量に応じた任せ方 | 「正解の所在」で手綱の長さを決める | P1, 01原理1 |
| 成果物で検収する目 | 完了報告でなく実機・実出力で判定 | P3 |
| 会議のファシリ・脱線の検知 | 「そもそも」による目的文への回帰 | P6 |
| 新人育成の段階的な任せ方 | レビュー通過率で自動化を昇格（※本人の宣言ベース。実行は未観測、01降格節） | 01[33][51] |
| 指摘の采配（今/後で/やらない） | レビュー指摘の三分仕分け | P6, 04[23] |
| 相手に合わせた説明の作り分け | 受け手別の成果物発注 | P11 |
| お手本を見せる指導 | 却下と同時に見本・参照物を渡す | P2, 01原理7 |

**移転方法**: 座学ではなく「追体験演習」を推奨する。raw/chunk-*.md から判断場面を10〜20件選び、「場面」と「引用の直前まで」を見せて A氏に判断させ、本人の実際の判断と突き合わせる。ズレた箇所がA氏の学習ポイントであり、同時にこの文書群の言語化漏れの検出にもなる（ズレの原因が文書にない場合、それは未言語化の暗黙知）。

## レイヤー2: 「向け直し」に必要な3つの解除（最重要・最初の壁）

人へのマネジメント感覚をそのまま持ち込むと失敗する箇所。向け直しではなく**既存の抑制の解除**が必要。

### 解除1: 遠慮の解除 — 試行はタダである
人相手の「多数の案を作らせて大半を捨てるのは失礼」という感覚を捨てる。本人は「確認が多すぎるな…全部画像作るようにスキルを修正して。確認は不要です」（01[26]）「もう一度根本原因をチームを作って様々な観点から考えて」（04[27]）を標準としており、選別だけに自分の認知を使う。A氏が人のマネジメント経験が豊富であるほど、この解除は難しい（丁寧に1案ずつ依頼→レビュー、という人間ペースに戻ってしまう）。

### 解除2: 記憶の期待の解除 — 相手は毎朝記憶を失う部下である
人間の部下は文脈を蓄積するが、AIはセッションで揮発する。「前に言ったのに」は通用せず、通用させたければ外部化（CLAUDE.md・スキル・参照物）するしかない。本人の運用: 逸脱の再発防止は説教でなく設定ファイル（02[38]）、resume時は次の一手が一意に決まる状態記述を渡す（04[08]）。

### 解除3: 信頼の前提の解除 — 遵守は保証されない
人には「約束したから守るだろう」が成り立つが、「LLMは必ず守ることは保証されない」（03[07]）。重要な制約は技術的ガードレール（hooks・deny設定・git）で封じ、最終ゲートだけ人間が握る（00[30]）。A氏が非エンジニアの場合、ガードレールの実装は誰かに任せてよいが、「仕組みで縛れないものは縛れていない」という認識自体は必須。

## レイヤー3: 新規獲得が要るもの（人マネジメントに対応物がない）

1. **迎合の検知＋自分の問い方の監査**。同意が続くこと自体を品質低下のシグナルとして扱う（03[10]）。対策の型: 「私の意見に引っ張られずに自分で考えて」の明示（02[66]）、別モデル・素のセッションでの独立検証（00[45][51]）。**重要な留保**: 本人自身に「〜ですよね？」と自分の傾きへの同意を求める誘導的な問い方の癖があり（04メタ観察）、検知器は自分の仮説に向いていない。A氏にはこの盲点込みで渡すこと（検知器だけ渡すと同じ盲点を複製する）。
2. **文脈量の設計**。渡しすぎは害（「人間の丁寧な指示文がAIにとって足かせになってる」03[02]）、渡さなすぎは事故。本人の実運用は前払いでなく「初手極小＋ズレた瞬間に精密投入」（01原理7）。言語コストの高いもの（質感・形式）は実物アンカーで渡す（P11）。
3. **視点の多重化**。「チームで考えて」による並列化、モデル別の適材適所（02[33]）。人の組織の「人数は有限」という制約感覚を捨て、視点数で品質を買う。
4. **検証の階層感覚**（A氏が非エンジニアの場合のみ新規）。一次情報への降り方（ログ・実測・公式・履歴）。本人はこれを26年の実装経験でやっており、同じ速度の移転は不可能。代替経路: 「検証そのものをAIチームに委任し、検証方法の妥当性だけ自分で判断する」型に組み替える。

## 移転しないもの（意図的に渡さない）

- **フィードバックの強度（怒りの運用）**。「しね！」（01[11]）「ちゃんとやれよ」（05[34]）は本人のスタイルであって原理ではない。ただし裏にある検知器は本物で、トリガーは「同じ指示の複数回無視」「却下理由の未反映」の2件にほぼ限定される（05メタ・02メタ観察）。渡すべきはその機能的等価物: 「トリガーを検知したら、言い方を強くするのではなく仕組み（スキル・設定・委任先）を変える」。
- **技術スタックの即断**（P1の一部）。ドメイン権威に依存する部分は移転不可。A氏は自分の権威領域（デザイン・業務知識など）で同じ構造を再現すればよい。

## 移転の成功指標（本人の流儀に合わせた設計）

本人の原理2（完了の定義は観測）をこの移転自体に適用する:
1. **判断一致率**: 追体験演習でのA氏の判断と本人の実判断の一致率。教材学習の前後で測る。
2. **手綱の分布**: A氏のAIセッションログで、丸投げ（短文委任）と精密指示の二極分布が再現されるか。中間だらけなら原理1が移転できていない。
3. **生成器修正率**: A氏が出力への不満を「その場の手直し」で終えず「スキル/プロンプト側の修正」に還元した割合（P2の移転確認）。

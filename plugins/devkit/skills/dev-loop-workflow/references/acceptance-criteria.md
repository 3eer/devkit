# 受け入れ条件ゲート（実装に入る前の門番）

> dev-loop-workflow の **Phase 1（設計・要件）** で dev-lead が番号付き受け入れ条件を確定する際の品質基準。

タスク説明から以下の3つを抽出する:

| 要素 | 内容 | 欠けていた場合 |
|------|------|--------------|
| ゴール | 何を作るか | 停止して確認する |
| 受け入れ条件 | **何が真になったら終わりか** | 停止して確認する（下記参照） |
| 制約 | 触ってよい範囲・やらないこと | デフォルト制約を適用して続行 |

## 受け入れ条件の品質チェック

- テストケースに翻訳可能な粒度か（「フィルタ適用中はフィルタ結果のみ出力される」は OK、「いい感じに動く」は NG）
- 異常系が1つ以上含まれているか。含まれていなければ、ゴールから異常系の受け入れ条件を1つ提案してユーザーに確認する（偽の収束対策）
- 受け入れ条件が1つも翻訳可能な粒度でない場合、これは実装依頼ではなく**設計相談の段階**。実装せず、確認質問を返して停止する

**受け入れ条件は番号付きで確定し、以降の全 Phase（特に Phase 6 のトレース）で参照する。**
ここで確定した一覧が、最後に「全部満たしたか」を照合する基準になる。

## デフォルト制約（明示されていない場合に適用）

- 受け入れ条件と無関係な変更（ついでのリファクタ等）を diff に含めない
- 依存パッケージの追加は禁止。必要なら停止して報告する
- 既存の public API のシグネチャ変更は禁止

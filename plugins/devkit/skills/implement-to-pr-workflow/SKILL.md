# implement-to-pr-workflow — 実装からマージ判断提出まで

**Input:** タスク内容＋受け入れ条件（＋制約）
**Output:** マージ可能な PR + Step 8 の Decision Brief（人間への「マージ／クローズ」二択）

## このスキルを貫く3原則（最重要・各ゲートはこの具体化）

1. **Decision-Ready** — 人間に**未整備のもの**を判断させない。全ゲートを通過させ、判断を
   「このPRをマージ or クローズ」の二択に圧縮してから渡す。**「全受け入れ条件を満たした」ことは
   自己申告でなく独立検証する**（Step 5）。URL を貼るだけの依頼は禁止（Step 8）。
2. **Live Proof** — 「テストが緑だから動くはず」「自信がある」で**実物確認を省略しない**。
   実物の動作面に対し、**テストコード以外の手段**で必ず1回は確認し、その証跡を提出する（Step 4）。
3. **push ≠ merge** — このスキルは **PR 作成までで止まる**。**AI は絶対にマージしない**。
   マージは人間の権限。ブランチを push し PR を立てるが、merge / squash / rebase-merge はしない。

このスキルの原理: **ループは与えた終了条件を最短で満たそうとする**。終了条件の穴（テスト改ざん・
偽の収束・スコープ膨張・**要件の取りこぼし**・**Live Proof の省略**・**勝手なマージ**）は
必ず突かれる前提で、各 Step のガードを省略しないこと。

**「緑になった」と「全部できた」は別物**: 受け入れ条件を1つ取りこぼしても、残りの機能のテストは
緑で通る。**完成の定義は「実装した」ではなく「全受け入れ条件が実物の証跡で満たされ、かつ
スコープ外の変更が無い」こと**であり、これを独立に検証するのが Step 5。

## Harness（Claude Code / Cursor 両対応）

| 操作 | Claude Code | Cursor |
|------|-------------|--------|
| サブエージェント | `Agent` → `devkit:requirements-checker` 等 | `Task` → `subagent_type="requirements-checker"` 等 |
| スキル委譲 | `Skill` → `qa-workflow` / `pr-review` | orchestrator が SKILL.md を `Read` し手順実行 |
| Live Proof（UI） | browser MCP / Bash | cursor-ide-browser MCP / Bash |
| Live Proof（API） | Bash `curl` / httpie | 同左 |

## 禁止事項・停止条件

- 既存テストの変更・削除・skip で「通す」ことは禁止。必要なら理由を報告して停止する
- 受け入れ条件と既存仕様が矛盾していたら、実装せず矛盾点を報告して停止する
- 検証ループ（Step 2）が5イテレーションで収束しなければ、原因分析だけ書いて停止する
- 同じエラーに2回連続で同じ修正を試みたら停止する（堂々巡り検知）
- 制約で許可されていない範囲のファイル変更・依存パッケージ追加は行わず、必要なら停止して報告する
- **Live Proof（Step 4）を、自信・テスト緑・「自明な変更だから」を理由に省略してはならない**。
  実物確認に必要な認証・環境が無い場合は、ゲートを誤魔化さず**何が必要かを正確に報告して停止する**
- **全受け入れ条件の達成が独立に検証される（Step 5）まで、PR作成・Decision Brief 提出に
  進んではならない**。未達の受け入れ条件が1つでもあれば「完成」と呼ばない
- **PR をマージしてはならない**。merge コマンド（`gh pr merge` 等）は実行しない

## Step 0: 受け入れ条件ゲート（実装に入る前の門番）

`$ARGUMENTS` から以下の3つを抽出する:

| 要素 | 内容 | 欠けていた場合 |
|------|------|--------------|
| ゴール | 何を作るか | 停止して確認する |
| 受け入れ条件 | **何が真になったら終わりか** | 停止して確認する（下記参照） |
| 制約 | 触ってよい範囲・やらないこと | デフォルト制約を適用して続行 |

**受け入れ条件の品質チェック:**
- テストケースに翻訳可能な粒度か（「フィルタ適用中はフィルタ結果のみ出力される」は OK、「いい感じに動く」は NG）
- 異常系が1つ以上含まれているか。含まれていなければ、ゴールから異常系の受け入れ条件を1つ提案してユーザーに確認する（偽の収束対策）
- 受け入れ条件が1つも翻訳可能な粒度でない場合、これは実装依頼ではなく**設計相談の段階**。実装せず、確認質問を返して停止する

**受け入れ条件は番号付きで確定し、以降の全 Step（特に Step 5 のトレース）で参照する。**
ここで確定した一覧が、最後に「全部満たしたか」を照合する基準になる。

**デフォルト制約（明示されていない場合に適用）:**
- 受け入れ条件と無関係な変更（ついでのリファクタ等）を diff に含めない
- 依存パッケージの追加は禁止。必要なら停止して報告する
- 既存の public API のシグネチャ変更は禁止

## Step 1: 実装

1. `coding-conventions` スキルの手順でプロジェクト規約・lint 設定を読み込む
2. 受け入れ条件を満たす最小の実装を行う（制約の範囲内で）
3. 受け入れ条件をテストコードに翻訳する（既存テストの流儀に合わせる）

## Step 2: 検証ループ（qa-workflow に委譲）

`qa-workflow` スキルの手順でテスト→修正→再テストを回す:

- 最大5イテレーション。停止条件・失敗パターン分類は qa-workflow の定義に従う
- 失敗テストの削除・skip は禁止（qa-workflow と共通）
- 5回で収束しなければ、原因分析を書いて**ここで停止**する（Step 3 に進まない）

## Step 3: 敵対的レビュー（pr-review に委譲）

`pr-review` スキルの手順で diff をレビューする。レビューの目的は承認ではなく**問題の発見**
（pr-review が並列起動する各エージェントは CRITICAL/HIGH/MEDIUM/LOW で報告する）。
**自分の書いたコードを自分で承認しない**——レビューは pr-review の独立エージェントに行わせる。

指摘の振り分け:

| 指摘 | 対応 |
|------|------|
| CRITICAL / HIGH（正確性・セキュリティ・仕様乖離） | 修正して **Step 2 に戻る**（再テスト必須） |
| MEDIUM / LOW・好みレベル | 修正せず Step 8 の Decision Brief に回す |

**往復の上限:** Step 2↔3 の往復は最大2周。2周で収束しなければ残課題を報告して停止する。
修正後に再テストを飛ばしてはならない。

## Step 4: Live Proof ゲート（実物 × テストコード以外で実証）

**緑になったテストは「壊れていない」証拠にすぎず、「実際に動く」証拠ではない。** Step 3 まで通過した
**最終形のコード**に対し、実物の動作面を**テストコード以外の手段**で1回起動・実行し、証跡を残す。

**変更種別ごとのモダリティ（どれか該当する手段を必ず1つ実行）:**

| 変更種別 | Live Proof の取り方 | 残す証跡 |
|---------|--------------------|---------|
| UI / 画面 | 実アプリを起動し browser MCP（cursor-ide-browser 等）で操作・スクリーンショット | 画像ファイルパス |
| HTTP API | サーバを起動し `curl`（または httpie）で実リクエスト | コマンド + status + レスポンス本文 |
| CLI / コマンド | ビルドして実コマンドを実行 | コマンド + stdout + exit code |
| ライブラリ / 純関数 | 最小スクリプト or REPL で import して呼ぶ | スクリプト + 実行出力 |
| バッチ / ジョブ | 実物大サンプルで1回実行 | ログ + 出力差分 |
| DB / マイグレーション | 実DB（またはコンテナ）へ適用し状態確認クエリ | before/after クエリ結果 |

**ゲート規定（Live Proof Gate）:**
- モック・スタブ・「テストが緑だから」での代替は**不可**。実物の動作面に当てる
- 受け入れ条件の**正常系を最低1本、異常系を最低1本**、テスト外の手段で再現する
- 証跡（コマンド／URL／出力／画像パス）は Step 8 にそのまま貼れる形で保存する
- 実物確認が**できない**（認証・環境・データが無い）場合は、ゲートを通過扱いにせず
  **何が必要かを明記して停止**する（= orchestrator の "Needs owner"。誤魔化して PR に進めない）
- Live Proof が**失敗**したら（テストは緑なのに実物が想定と違う）、その挙動を捕捉する
  テストを1本追加してから **Step 1 に戻る**。この差し戻しは最大1回。2回目で失敗したら、
  仕様と実装の乖離として原因分析を書いて停止する

## Step 5: 完了判定ゲート（要件トレーサビリティ・独立検証）

**「実装した」ではなく「全受け入れ条件が実物の証跡で満たされ、スコープ外の変更が無い」を独立に確認する。**
自分が埋めた表を自分で承認しない——`devkit:requirements-checker` エージェントを **Agent ツールで起動**し、
Step 0 で確定した番号付き受け入れ条件・diff・各テスト名・Step 4 の Live Proof 証跡を渡して双方向に照合させる。

**双方向トレース（どちらの欠落も「未完成」）:**

| 方向 | 検知するもの | 判定 |
|------|------------|------|
| 順方向（充足） | 各受け入れ条件に「実装箇所 × テスト名 × Live Proof 証跡」が揃っているか | 1つでも欠ければ **未達** |
| 逆方向（スコープ） | どの受け入れ条件にも紐づかない変更が混ざっていないか | あれば **スコープ外** |
| 意図の一致 | テストは緑だが受け入れ条件の**意図**を満たしていない（文面だけ通している）ものはないか | あれば **未達** |

出力として**トレーサビリティ・マトリクス**を生成する（Step 8 の Decision Brief でそのまま使う）:

| # | 受け入れ条件 | 実装箇所 | テスト名 | Live Proof | 状態 |
|---|------------|---------|---------|-----------|------|
| 1 | … | `src/…` | `test_…` | `curl …` の出力 | ✅ |

**ゲート判定:**
- **未達が1つでもあれば BLOCK**。PR / Decision Brief に進まず **Step 1 に戻る**。
  この差し戻しは最大1回。2回目でも未達なら、何が満たせていないかを明記して停止する
- **スコープ外の変更**は、削除して Step 2 からやり直すか、削除できない理由を Step 8 に明記する
- 全条件が ✅ になって初めて「完成」。ここを通らない限り Step 6 へ進めない

## Step 6: コミット（push 前）

1. `git status` で未コミット変更を確認する
2. 作業ブランチに居なければブランチを作成する（デフォルトブランチへ直接 commit しない）
3. 変更がステージされていなければ、受け入れ条件に関連するファイルのみ `git add` する
4. Conventional Commits 形式で `git commit` する（既に適切な commit がある場合はスキップ可）
5. 意図しないファイル（`.env`、credentials 等）が含まれていないか確認する
6. **未コミットの実装変更が残っている状態で Step 7 に進まない**

## Step 7: PR 作成（push する。マージはしない）

1. ベースブランチを `git log` / リモート HEAD から自動検出する（決め打ちしない）
2. 受け入れ条件・Step 5 のトレーサビリティ・マトリクス・Live Proof 証跡・レビュー結果を含む
   PR body で `gh pr create` する
3. ブランチを push し PR の canonical URL を取得する
4. **ここで止まる。`gh pr merge` 等のマージ操作は絶対に実行しない**

## Step 8: マージ判断の提出（Decision Brief・終端）

**前提: Step 5 が全 ✅ でなければここに来てはならない。**

**「URL ＋ "マージ？"」だけを投げるのは禁止**（orchestrator: *Never emit a bare URL plus land/delete*）。
人間が**10秒で判断できる**よう、以下の構造で提出する。report を綺麗にまとめる方向に最適化せず、
グレーな判断は必ず「残存リスク・自信がない箇所」に出す:

```markdown
## マージ判断のお願い — [タスク名]

PR: https://github.com/OWNER/REPO/pull/NN   ← canonical な完全URL（#NN 不可）

### 何を変えたか
- [1〜3行]

### 受け入れ条件の達成状況（Step 5 のトレーサビリティ・マトリクス）
| # | 受け入れ条件 | 状態 | 根拠（テスト名 / Live Proof） |
|---|------------|------|----------------------------|
| 1 | [条件1] | ✅ | `test_xxx` / `curl …` の出力 |

（全 ✅ であること。スコープ外の変更があればここで列挙し理由を書く）

### Live Proof（テストコード以外の実証）
- 手段: [browser / curl / CLI / script]
- 証跡: [コマンド・URL・出力・画像パス。正常系/異常系それぞれ]

### レビュー結果
- CRITICAL / HIGH: 0件（あれば修正済みの一覧）
- 残 MEDIUM / LOW: [一覧、または「なし」]

### 残存リスク・自信がない箇所
- [グレーな判断・推測で進めた箇所。なければ「なし」と明記]

### 推奨
- [merge 推奨 / 見送り推奨 とその理由]

---
→ このPRを **マージ** しますか、**クローズ** しますか？（私はマージしません）
```

最後の一文（「私はマージしません」）で push≠merge の境界を明示し、ここで停止する。

## 失敗モードとこのスキルのガード対応表

| 失敗モード | 何が起きるか | ガード |
|-----------|------------|--------|
| テストの改ざん | 通らないテストを「修正」して緑にする | 禁止事項1行目 + qa-workflow の禁止規定 |
| 検証の形骸化 | レビューが「LGTM」になる | pr-review の重大度分類・敵対的観点・自己承認の禁止 |
| **緑だが動かない** | テストは通るが実物は壊れている | **Step 4 Live Proof ゲート（テスト外・実物で実証）** |
| **実証の省略** | 「自信ある／自明だから」で Live Proof を飛ばす | **Step 4 のゲート規定（waiver 禁止・不可なら停止）** |
| **要件の取りこぼし** | 受け入れ条件を1個忘れても残りのテストは緑で通る | **Step 5 完了判定ゲート（順方向トレース）** |
| **スコープ外の混入** | どの受け入れ条件にも紐づかない変更が紛れる | **Step 5 完了判定ゲート（逆方向トレース）** |
| **意図の不充足** | テストは緑だが受け入れ条件の意図を満たさない | **Step 5 の意図一致チェック（requirements-checker）** |
| **未コミットのまま PR** | diff がリモートに載らない / 不完全な PR | **Step 6 コミットゲート** |
| **勝手なマージ** | AI が自分でマージして取り返しがつかない | **3原則3（push≠merge）+ 禁止事項末尾 + Step 7/8** |
| 未整備で判断要求 | 半端な状態で人間に「どうします？」 | **Step 8 Decision Brief（二択に圧縮）** |
| スコープ膨張 | ついでのリファクタで diff が読めなくなる | Step 0 デフォルト制約 + Step 5 逆方向トレース |
| 偽の収束 | エラー握りつぶしで緑にする | Step 0 の異常系チェック + Step 4 異常系の実証 |
| 堂々巡り | 同じ修正を繰り返してトークンを溶かす | 停止条件（同一修正2回で停止） |
